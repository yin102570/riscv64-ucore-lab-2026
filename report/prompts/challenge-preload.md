# Challenge：用户程序的预加载方式

## 1. 问题

指导书问：用户程序是何时被“预先加载到内存”的？与常用操作系统有什么区别，原因是什么？

## 2. 我们的回答

要区分三个时刻：

1. **构建时**：`user/*.c` 被编译、链接成 ELF（`obj/user/exit.out`），再由 `objcopy -I binary` 变成内核镜像里的只读字节数组（`obj/__user_exit.out.o`）。
2. **内核启动时**：这段字节数组随 `bin/ucore.img` 一起被 QEMU 装入物理内存，但它只是内核镜像的一段数据，不是用户进程的地址空间。
3. **执行 `exec` 时**：`user_main()` 调 `kernel_execve()`，`load_icode()` 解析 ELF，建立新的 `mm` 和页表，把各 `PT_LOAD` 段拷贝到用户虚拟地址，建立用户栈，最后改写 trapframe。到这一步，用户程序才真正“进入”用户地址空间。

所以“预加载”指的是程序镜像在构建时嵌入内核，而不是用户页在开机时就建好。用户页仍然是 `load_icode()` 执行时按段建立的。

与常用 OS 的差异：

- 常用 OS 从文件系统按路径读取 ELF，ucore 没有文件系统，程序名只是内核符号。
- 常用 OS 支持按需分页，代码页第一次访问才从磁盘读入；ucore 在 `load_icode()` 里一次性映射并拷贝所有段。
- 常用 OS 支持动态链接和共享库；ucore 的用户程序是静态链接的独立镜像。

原因是 Lab5 要验证的是进程创建、地址空间和系统调用，不是文件系统。把程序嵌入内核可以让测试完全可复现，不依赖外部存储；代价是内核镜像变大，替换程序必须重新编译内核。
